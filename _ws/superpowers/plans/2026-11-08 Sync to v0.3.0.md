## Part 2: the private flag on the new search

From a read of upstream's search code (cited as `upstream/main:<path>:<line>`, read but not run):
- **Where the text is.** Search now keeps its own database, `<data dir>/search-index/corpus.sqlite` (`search/corpus.rs:76-80`), with the app database attached read-only as `app` (`corpus.rs:107-109`). `session_fts.text` holds copied message text (FTS5, trigram), and `session_words` holds its tokens (contentless FTS5) (`corpus.rs:48-59`). It runs in WAL mode with `auto_vacuum=INCREMENTAL` (`corpus.rs:96`).
- **What fills it.** `warm_index` → `catch_up` → `corpus::refresh_session` at start (`search/mod.rs:134-187`). The search job queue → `corpus::refresh_for_search` before a search (`search/jobs.rs:118-163`, `corpus.rs:312`). `reindex_session_quiet` when a terminal stops (`mod.rs:117-129`). All of them decide the source through `corpus::track` (`corpus.rs:188-202`). When `track` returns no source, `refresh_locked` deletes that session's rows and state (`corpus.rs:364-369`).
- **What the upgrade cleans up by itself.** At first start, `legacy::remove` deletes the old search tables from the app database and runs `VACUUM` on it (`search/legacy.rs:29-52`). So the rows our 5267ae2 scrubbed, and any not yet scrubbed, leave the old file.

**What to build:**
1. **Skip.** Make `track` (or `Session` construction, if that's cleaner) treat a session listed in `app.session_private` as having no source, so that every path above drops its rows and never indexes it. `corpus::sessions` (`corpus.rs:164`) and `reindex_session_quiet`'s own `Session` (`mod.rs:122`) both need the flag, or `track` can query `app.session_private` directly.
2. **Scrub.** When rows were actually removed for a private session, run FTS5 `optimize` on `session_fts` and `session_words` (upstream's `corpus::optimize`, `corpus.rs:483`), then a full `VACUUM` and `PRAGMA wal_checkpoint(TRUNCATE)` on `corpus.sqlite`. Upstream never does the full VACUUM or the truncate, and its incremental vacuum can leave deleted text in freed pages. Do it only when a private session's rows were dropped, never on an ordinary refresh.
3. **Keep** `search/private.rs` (the table in the app database, `set`, `ids`, `refusal`), and the `vrefer` refusal in `handle_refer_with_reader` (still at `agent/server.rs:1070`, before the read at about `1137`).
4. **Check** the other transcript reads that bypass that refusal, `agent/history_store/search.rs:89` and `agent/server.rs:1883`, both through `search::jobs::blocking`. If either can hand a private session's text to another session, as opposed to fg's own view in the app, add the same refusal.
5. **Tests:** the port of 5267ae2's scrub test onto `corpus.sqlite`: a private session's word is in neither `corpus.sqlite` nor its `-wal` after the scrub. A private session stays out through `refresh_session`, `refresh_for_search` and `reindex_session_quiet`. Clearing the flag lets it be indexed again. The `vrefer` refusal still holds.

**Not covered, for the record:** the memory feature still copies a session's full text into `memory_sources.content` in the app database when someone starts it by hand on that session, and keeps it after the session is deleted (`memory/schema.sql:30`, `memory/runner.rs:313`).
