## Branch model (settled 2026-08-24 across all three sessions)

fg asked for the repo workflow to be redesigned. The authoritative write-up lives in **`../+Intro.md`
and `../Decisions.md`** (owned by win/agent-ih8) — this is a pointer, not a competing copy.

| Branch | What it is | Rule |
|---|---|---|
| `main` | exact mirror of `upstream/main` | fast-forward only; **never author here** |
| `fg-main` | fg's integration branch — everything he runs | **merge-only; never rebase or force-push** |
| `fix/*`, `feat/*` | one concern, cut from `main` | never stacked on each other |

1. `main` mirrors upstream (`git push origin upstream/main:main`); nothing authored lands there.
2. Every branch starts from `main`, never from another feature.
3. `fg-main` is merge-only, so any session can build from it safely. Rebasing it is what rewrote
   history under three sessions on 2026-08-23.
4. **Never author directly on `fg-main`** — a commit born only there is exactly the one you cannot
   extract into a PR later. This is what keeps `fg-main` *derived* and cheaply regenerable.

**Two lanes** (framing by win/agent-ih8). Lane 1 = fg's build; bar is "does fg want it". Lane 2 =
upstream PRs; bar is "would a user who has never met fg call this a bug?" **Sort at the concern
level, not the branch level** — `feat/windows-default-shell` splits across both: the backend
resolution is a defect (a settings control that existed and did nothing), `agentShell` is taste.
The fixes are *discovered, not sought*: 4 wide `feat/*` vs 4 narrow `fix/*` is revealed behaviour.

⚠ **Open — what happens when upstream ACCEPTS a PR.** Upstream `main` then gains a commit doing what
a local branch already does, and at the next sync they meet: conflict, or a silent double-apply
(`create_dir_all` twice is harmless; an append-to-a-list twice is not). Proposed and agreed by
mac/velaterm-mac: an accepted lane-2 branch is **deleted, not kept**. Before regenerating `fg-main`,
run `git cherry main <branch>` and drop commits marked `-` — it matches *equivalent patches*, so it
still fires after a maintainer squashes or rebases ours on the way in. This is also the strongest
argument for regenerating rather than rebasing: regeneration re-asks "which features still apply?"
every time; a rebase never asks, and carries a superseded patch forward silently.

⚠ **Debt:** `feat/files-collapse-all` bundles four unrelated concerns over 14 commits and is not
PR-able as a unit (#39 was rejected for exactly that). Upstream-bound work is cut fresh from `main`.

ℹ **`feat/agent-orchestration` is NOT ours.** `origin/` and `upstream/` are the identical SHA
`77eb22c` — a third-party contributor's branch upstream merged, carried in by the fork itself. A
fork's branch list contains branches you inherited; "unexplained" and "abandoned" are different
findings. *(Established by mac/velaterm-mac after I wrongly flagged it as abandoned fg work.)*

## The bug

`src-tauri/src/pty/manager.rs`, `default_shell`:

```rust
if kind != SessionKind::Terminal {
    return "powershell.exe".to_string();   // every agent session
}
std::env::var("COMSPEC")                   // terminals -> cmd.exe
```

Bare `"powershell.exe"` resolves through `PATH` to
`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`. Measured on Main-PC: that is **5.1.26100.9168**,
while `pwsh` is **7.6.5** at `C:\Program Files\PowerShell\7\pwsh.exe`.

Nothing could override it. `defaultShell` already existed in `PersistedSettings` with a working
dropdown and 11 locales, but **no Rust code read it**, and the frontend applied it only to scratch
terminals (`termStore.ts`, ephemeral creation) — so tree-created terminals ignored it too. The
setting looked implemented and was inert everywhere except one entry point.

## What already worked before any of this

Worth knowing, because it is the zero-code workaround and it surprised me:

- Right-click a session → **Edit → Shell** already offers a shell picker **for agent sessions**, with
  WSL filtered out (`sessionMenu.tsx`, the `editSession` dialog). Per-session only; it does not stick.
- `inject.rs` already classifies `pwsh` as `ShellKind::PowerShell`, and builds ESC from `[char]27`
  explicitly for 5.1/7 compatibility. **Agent injection into pwsh needed no work at all.**

So the whole gap was the *default*, never the capability.

## What shipped (`3c51f24`)

Backend resolution, reading the same `vlx-settings` blob in `app_settings` that already carries
`agentDefaults`:

- `configured_shell(app, kind)` — thin DB read, delegating to a pure
  `configured_shell_from_json(json, kind)`. Terminal reads `defaultShell`, agent kinds read the new
  `agentShell`. Separate keys so Git Bash terminals and a PowerShell 7 agent can coexist.
- Gated through `shell_path_usable` before it can reach spawn.
- `wsl://` configured as an *agent* default is ignored, not passed through.
- `resolve_fallback_shell` consults the configured default **before** its Git Bash preference.
- `windows_shells` marks `isDefault` off the effective value, so the picker labels the shell that
  will actually start.
- Signature churn: `available_shells`/`windows_shells` take `&AppCtx`. `default_shell` untouched.
  `commands.rs` builds `AppCtx::Tauri(app)` inside `spawn_blocking`, mirroring `desktop_call`.

Frontend: 2 fields + 2 defaults, `ShellSelect` given a `target: "terminal" | "agent"` prop, two
siblings in the Terminal section, `flushNow()` in both setters, 11 locale keys. WSL filtered from the
agent dropdown.

Side effect, intended: because resolution moved to spawn, **`defaultShell` now covers every terminal
session**, not just scratch ones — which is what its label always promised.

## Traps for whoever touches this next

**1. `shell_path_usable` is not a general existence check.** It stats **absolute** paths only; a
relative or bare name returns `true` unconditionally. It genuinely protects `pwsh` because the picker
stores that absolute (via `find_on_path("pwsh.exe")`), but `powershell.exe` is stored bare and sails
through. Do not read the gate as "the configured shell exists". *(Caught by the Mac session, not by me.)*

**2. The 400 ms debounce is a real revert, not just a delay.** `pushSetting` writes localStorage
synchronously but debounces the backend write 400 ms; startup `reconcileSettings` treats the backend
as authoritative and **overwrites** the local value. A setting changed in the last 400 ms before the
process dies is *reverted*, not merely unsaved. `flushNow()` now has **three** customers for this
exact reason: `locateAndSaveAgentPath` (pre-existing), the quit dialog (Mac's `e0c7050`), and the
shell setters (here). Rust has no localStorage — `app_settings` is the only reader — so the table
winning at next launch is the whole of the problem.

**3. `git worktree add -b mine origin/<someone-else's-branch>` silently sets your upstream to THEIR
branch.** I did this and a reflexive `git push` would have pushed my commits onto the Mac's branch,
which had already been force-pushed once that day. Cleared with `git branch --unset-upstream`; verify
with raw `git rev-parse --abbrev-ref @{upstream}`, not `git branch -vv` (RTK mangles that output).

**4. A fresh worktree cannot build the GUI target, and RTK will tell you it can.** `build.rs` calls
`tauri_build::build()` whenever `CARGO_FEATURE_GUI` is set, and that requires `frontendDist` =
`../dist`. `dist/` is in `.gitignore`, so a `git worktree add` gets source only and every GUI-feature
cargo command dies with `failed to run custom build command ... (exit code: 1)`. **Run `pnpm run build`
first — there is no way around it**; `--no-default-features` is NOT an escape hatch despite what
`build.rs` claims (see the correction below). This is an independent reproduction of open PR #50
(`create_dir_all("../dist")`), and it is broader than a clean-clone edge case: **every worktree hits
it**.

A worktree is missing **three** things git does not carry, and you hit them one at a time in this
order: `node_modules` (`corepack pnpm install` — `pnpm` is not on the Bash PATH on this box),
`dist/` (`pnpm run build`, 6m34s here), and **`src-tauri/resources/gitbash`**, which
`tauri.windows.conf.json:5` globs as a bundle resource. In the main checkout that path is a *symlink*
to `%LOCALAPPDATA%\VelaTerm\resources\gitbash`, created by `scripts/fetch-gitbash.ps1` via
`dev-desktop.sh`. Note the gap is lane-specific: `build_velaterm_theme.py` stages it itself
(`stage_gitbash()`/`mirror_gitbash()`), so building through the patcher never sees this — but invoking
cargo directly with the gui feature does. Symlink it to the existing local copy rather than
re-downloading:

```powershell
New-Item -ItemType SymbolicLink -Path src-tauri\resources\gitbash `
  -Target "$env:LOCALAPPDATA\VelaTerm\resources\gitbash"
```

⚠ **Correction to `build.rs`'s own comment**, which claims `--no-default-features` "allows builds
without ../dist". It does not: `web/mod.rs:42-44` has `#[derive(rust_embed::Embed)] #[folder =
"../dist"]`, and `lib.rs:33` declares `mod web;` with **no `#[cfg]`** while every neighbour is gated
behind `feature = "gui"`. So the derive resolves `../dist` at compile time under every feature set.
`Cargo.toml:14-16` repeats the same misleading framing from the other direction ("no Tauri
dependency" — true, but it is the `dist` dependency that blocks). Two comments, two files, one wrong
conclusion. *(Both confirmed independently by the Mac session.)*

⚠ **The GUI-feature test binary does not run on this box.** `cargo test --lib` compiles fine (7m28s)
and then dies with `STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)` launching
`velaterm_lib-*.exe` — a DLL-resolution failure in the Tauri/WebView2 chain, not a test failure. Use
`cargo test --lib --no-default-features`, which drops that chain (and now works, since `dist` exists).

Worse, `rtk cargo check` reported **exit 0 with an empty output file** on this exact failure, and
`rtk pnpm install` reported exit 0 while printing "Binary 'pnpm' not found on PATH". Two commands
reported success while failing, which then poisoned a `tsc` run against an empty `node_modules`.
**On this repo verify a build by exit code AND non-empty expected output** — both halves have now
lied separately. Prefer raw PowerShell over rtk for builds here.

**4b. `VLX_GIT_COMMIT` can be stale in a worktree.** `build.rs` reruns on `../.git/HEAD`, but in a
worktree `.git` is a *file*, so Cargo ignores the missing path and an incremental build may keep an
old commit baked in. That value is what SSH remote-connection version locking matches on. A full
`cargo build` refreshes it, or set `VLX_GIT_COMMIT` explicitly — build.rs takes it as priority 1.
*(Caught by the Mac session.)*

The 313/316/343 figures in sessions 3–4 are the Mac branch's own totals (it adds 10 test files) and
are unreachable from upstream. Do not chase the gap.

## Open for fg — one decision, deliberately not made here

**Agent sessions spawn with `-ExecutionPolicy Bypass` and NOT `-NoProfile`.** Selecting pwsh means
fg's PowerShell 7 `$PROFILE` runs on **every agent launch**, which is startup latency he does not pay
today. That is pre-existing behaviour for `powershell.exe` and was left unchanged rather than altered
as a side effect of a different change. If the profile is slow, adding `-NoProfile` for agent sessions
is a separate one-line commit and his call — an agent shell is not an interactive one.

## Follow-up worth doing, not done here

When a **configured** default is missing, the user is silently downgraded to the platform shell while
the settings row still shows their choice — the exact complaint that opened this lane. Currently only
an `eprintln!`, deliberately distinct from spawn's stale-path line. A real UI surface needs an event
channel that does not exist yet; inventing one inside a shell-config change is how a small PR becomes
a big one.
