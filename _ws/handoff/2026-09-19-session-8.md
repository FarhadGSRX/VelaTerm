## What made 23 conflicts tractable — re-merge against last sync's tree

The feature branches are based on `ea6236a` (v0.1.102, now ten releases back), so git's three-way merge
uses a base that predates almost everything upstream has done. But `7deb188` — last sync's reconciled
tree — already carries our features *on top of `7dd2b0b`*. So for each conflicted file:

```
base   = 7dd2b0b:F     (previous upstream)
ours   = b570e29:F     (new upstream)
theirs = 7deb188:F     (previous fg-main after its reconcile; 1df00aa for the second merge)
git merge-file -p ours base theirs
```

That applies last time's resolution onto the new upstream and conflicts only where upstream moved those
lines since. 20 conflicts became 7 clean (termStore.ts included, despite +421 upstream lines) and 13 with
one or two hunks that were genuinely new. The previous reconcile commit's fixes to *non*-conflicted files
re-applied as a patch: `git show 7deb188 -- <7 files> | git apply --3way --index` — all clean.

This is what "read the previous reconcile commit first" turns into operationally. Runbook step 4 now
carries it.
