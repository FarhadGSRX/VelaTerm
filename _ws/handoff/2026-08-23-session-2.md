- `CI` drives non-colour behaviour (non-interactive prompts, progress rendering); stripping it could

## Gotchas found the hard way

- **The vitest `forks` pool is broken on the Windows box.** Runs reported `Failed to start forks
  worker` 11–30 times; one run executed a single test file out of 31 and would have looked like a
  catastrophic regression. **Always use `vitest run --pool=threads` here.** With threads, all 31 files
  run. Baseline comparison, same pool, same machine: upstream/main 7 failed / 23 passed (30 files);
  with our commit 7 failed / 24 passed (31) — identical failure count, the +1 being our own test. The
  failing *sets* differ by one file in each direction run to run; that is the known flakiness.
- **Never pipe a background Bash command through `tail`** — it buffers until exit, so the log stays
  0 bytes and a running build looks dead. Cost a wrong "the build failed" conclusion.
- **`cargo` cannot relink while a dev instance is running**: `failed to remove file
  target\debug\velaterm.exe — Access is denied. (os error 5)`, exit 101. Close the old dev window
  first. `dev-instances.cjs ls` reports "No dev instances are running" even when one is, so check
  `tasklist | grep velaterm` instead.
- **Colour behaviour cannot be tested from the agent's Bash tool** — it has no TTY, so every tool
  disables colour regardless of `NO_COLOR`. Runtime colour claims need a real terminal.
- **fg's shell is PowerShell.** `$NO_COLOR` is a bash-ism and silently expands to empty there; use
  `$env:NO_COLOR`. Also never pipe the probe through `head`/`Select-Object` — that removes the TTY
  and disables colour, destroying the test.
- The repo is **pure LF** (`git ls-files --eol` → `i/lf w/lf`, `core.autocrlf=false`), so `sed -i` is
  safe here. That is the opposite of the patcher's checkout — do not carry the assumption across.
- **VelaTerm's theme selector is in the titlebar, top right** (monitor / moon / sun icons), not in the
  Settings panel.

## Verifying a change without CI

Upstream has no CI and a red baseline, so the working method is: reproduce the defect, apply the fix,
reproduce the pass, and **prove the test fails without the fix**. Both PRs this session did that.
`rustfmt --check` diff-line count before vs after is a cheap way to show a Rust change adds no
formatting drift (140 either way for #52).

### Two corrections worth keeping

- **No Gatekeeper workaround belongs in the macOS instructions.** We expected a quarantine block and
  prepared an `xattr -d com.apple.quarantine` / right-click→Open step. It never applied:
  `com.apple.quarantine` is set by the *downloading* agent (browser, Mail, AirDrop), so a locally
  compiled binary never carries it and never meets the gate — unsigned or not. `codesign -dv` shows
  unsigned and `spctl -a` would reject, but neither check fires. It just launches. This starts to
  matter only when a `.dmg` is handed to another machine — the same moment the TCC item above does.
- **The vitest forks-pool break is Windows-only — confirmed.** macOS default forks pool: 30/30 files,
  222/222 tests, 18.8s. So **scope the `--pool=threads` workaround to Windows**; do not pin it in
  `package.json` or any CI config, or you slow the Mac and CI to route around a bug that isn't there.
