## The four things worth knowing before the next sync

**1. The Mac feature branches are a STACK, not siblings.**
`ux-settings ⊂ file-tree-favorites ⊂ sticky-pane ⊂ files-collapse-all`, verified with
`git merge-base --is-ancestor`. So a regeneration merges the **tip** plus the independent branches —
three merges, not six. The cost lands at the PR boundary: any of the lower three sent upstream as-is
would carry its ancestors' commits, so each needs rebasing onto `main` first. Recorded in `+Intro.md`.

**2. Upstream bumped `MIRROR_LAYOUT_VERSION` 1 → 2** for their new sidebar-view mirroring.
`sanitizeMirrorLayout` rejects a mismatched `v` outright, so **a v0.1.105 client will not mirror with
a v0.1.103 client at all**. Both machines must be on `3411de7` before mirror mode works between them.
Two of our tests hardcoded `v: 1` and failed; they now read the module's constant.

**3. Regeneration earned its keep twice, in ways a rebase would not have.**
- Our quit-dialog commit (`9dd9e64`, PR #54) landed upstream as `2ac14ca` and upstream then went
  *further* — a re-entrancy guard on the confirm button and a bounded flush. Our side was a strict
  subset whose inline button styles would have fought the new CSS classes. Taken from upstream
  entirely. A rebase would have replayed our weaker version as a conflict to hand-resolve.
- `git cherry` reported **zero** commits already upstream, for all six branches. Patch-ids had
  drifted, so it could not see #54 at all. The merge did.

**4. v0.1.104/105 rewrote the settings controls one level below where they were checked.**
`win/velaterm-winshell` verified `<Field label={t("settings.defaultShell")}>` still existed at
`56dad0f:148` and concluded the churn was cosmetic. The Field did survive — but upstream replaced

⚠ **One test HANGS on Windows and the suite never finishes without skipping it.** Two Windows-only
suite flags, both now required:

```
cargo test --lib --no-default-features -- --skip wait_capture_does_not_expire_before_late_first_prompt
npx vitest run --pool=threads --maxWorkers=2
```

**Cause A (established):** upstream test fixtures build JSON by interpolating a Windows path —
`server.rs:1087`, `resume.rs:844` — so `C:\Users\...` puts `\U` and `\f` into the string raw and
`serde_json` rejects it. The hang is this at `resume.rs:844`: the rollout file is invalid JSON, so
`wait_for_codex_session` never matches and loops forever.

**Cause B — SOLVED, and it is two causes. Both CONFIRMED on both machines.**

**B1 — `core.autocrlf`, and it is a CONFIG bug, not a Windows one.** `init_repo()` pins
`user.email`, `user.name` and `commit.gpgsign` but **not** `core.autocrlf`, so a temp repo inherits
the global. `discard()` runs `git checkout -- <path>`, smudge applies, and the working tree comes
back CRLF against assertions expecting `"hello\n"`. Reproduced on **macOS** by setting `autocrlf=true`. Stronger than that, though: on Windows the
value is set by the **Git-for-Windows installer at `--system` scope**, and a bare temp repo inherits
it — so these two tests fail for **every default Windows install**, not merely for someone who opted
in. (macOS leaves it unset at all scopes, which is why they pass here.) ⚠ Diagnose with
`git config --show-origin`: reading `--global` alone returns empty on Windows and reads as clean. Windows proved it by injecting
`GIT_CONFIG_KEY_0=core.autocrlf VALUE_0=false` (touching nothing of fg's): `16 passed; 2 failed`,
up from `14 passed; 4 failed`.

⚠ **I cleared this hypothesis wrongly the first time and the mistake is worth keeping.** I probed
`git show HEAD:a.txt`, which reads the blob and by design never runs the smudge filter — the one read
path where the mechanism cannot appear. The failing assertions read the **working tree**. Right
hypothesis, wrong object, clean negative, reported as a disproof. **A passing check disproves nothing
unless you have shown it can produce a positive.**

**B2 — `worktree_remove` is broken on Windows. A PRODUCT bug, not a test artifact.** `git.rs:883-885`
runs `git -C <worktree> worktree remove --force <worktree>` — cwd set inside the directory being
deleted. POSIX permits that; Windows refuses. Measured `exit 0, removed` on macOS and
`exit 255, Permission denied, worktree survives` on Windows. **Any Windows user removing a worktree
from VelaTerm's git panel hits this.**

Fix notes for the PR:
- **Not "one argument."** `worktree_remove(path, force)` never receives the repo root. It must resolve
  it first — `git -C <wt> worktree list --porcelain | head -1` gives the main worktree, and *reading*
  a cwd is fine on Windows; only deleting it is not.
- **The sibling already does it right:** `worktree_add` uses `-C` at the repo top (`git.rs:343-344`).
  So the fix makes remove match the file's own convention rather than adding a platform special-case —
  a much easier sell to a maintainer.
- **Blast radius is exactly one function.** Of the four `-C` sites in `git.rs`, the fourth
  (`push_branch`, `git.rs:927`) is *not* the same bug: push does not delete its cwd. No sweep needed.

**"Cause A, ten tests" was WRONG and was retracted by Windows.** `--nocapture` across the whole
suite showed the ten do not share a cause — two are JSON-parse failures, the rest present as missing
hook entries, `None` returns, a 404, and an OS path rejection. The JSON mechanism was confirmed on two
tests and the other eight were attached by neighbourhood. The retraction's own line is the keeper:
**an inference stated as a grouping still propagates as a finding** — a grouping is more contagious
than a wrong claim, because the next reader inherits it as structure rather than as an assertion.

`std::thread::current().name()` into a directory name; a throwaway crate confirmed libtest sets that
